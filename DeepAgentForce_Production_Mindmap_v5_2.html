身份、权限与工具选择 9 个术语
required_scopes
必需权限范围

工具声明的调用门槛。比如查询订单要求 orders:read，取消订单要求 orders:cancel；用户没有对应权限，工具即使语义最匹配也不能进入可执行候选。

Principal
已认证身份主体

服务端从已验证登录凭证中解析出的用户身份及其租户、角色等信息。不能直接相信请求体里用户自己填写的 user_id 或 tenant_id。

Scope
权限范围

一项具体操作权限，例如 files:read、orders:cancel。它比“管理员 / 普通用户”这种角色更细，适合控制工具能做什么。

RBAC
基于角色的访问控制

先给用户分配角色，再由角色获得权限。例如财务角色能查账单，客服角色能查订单；执行具体工具时仍需检查资源归属。

Tenant
租户

SaaS 系统里相互隔离的客户组织。A 公司用户的文档、会话和记忆不能被 B 公司检索到。

Capability Contract
能力契约

把某一步任务说清楚：要做什么动作、作用于什么对象、需要什么前置条件、返回什么结果、会不会产生副作用。例如“查询订单状态”与“取消订单”是两份不同契约。

Tool Registry
工具注册目录

系统登记所有可用工具的目录，保存工具用途、参数格式、权限要求、版本、超时和健康状态；不是把所有工具代码直接塞进模型提示词。

JSON Schema
JSON 参数结构规范

规定参数字段、类型、必填项、枚举和范围。例如 order_id 必须是字符串、reason 必须在允许枚举内；服务端用它拒绝模型生成的非法参数。

MCP
模型上下文协议

一种让 Agent 以统一协议发现和调用外部工具 / 资源的接入方式；它解决连接规范问题，不自动替代身份授权、参数校验和调用审计。

上下文、意图与 Agent 执行 12 个术语
Context Manifest
上下文清单

记录某一次模型调用实际装入了哪些历史消息、检索片段、记忆、工具说明及其版本和 Token 用量。排查错误答案时，可以还原模型当时看到了什么。

Context Window
上下文窗口

模型单次请求最多能接收的 Token 容量。系统提示、历史、RAG 证据、工具定义和预留输出都占用它。

Token Budget
Token 预算

给本次请求各类内容分配的 Token 上限。例如先预留系统规则和 2,000 个输出 Token，再把剩余空间分给历史、检索证据和记忆。

Prompt Injection
提示词注入

把恶意指令藏在网页、文档或工具返回内容里，诱导模型忽略系统规则。外部内容必须当作数据而非可信指令，并由服务端执行权限检查。

意图识别
判断用户要完成的任务类型

例如区分“解释订单状态”（查询 / 解释）和“取消订单”（写操作）。意图识别只给出任务判断，不代表已经获得执行权限。

DAG
有向无环任务图

把多步任务表示为带依赖关系的步骤图。比如先查订单，再判断是否可取消，最后取消；后一步必须等前一步完成。无环是为了避免计划互相等待。

Step Ledger
步骤账本

逐步记录每个任务步骤的唯一 ID、输入摘要、执行状态、尝试次数和结果引用。Worker 重启后先查账本，避免重复执行已经成功的步骤。

Observation
工具执行观测结果

工具调用后返回的结构化结果，包括成功 / 失败状态、业务数据、错误码和外部单号；Controller 根据它判断下一步，而不是只读模型说“完成了”。

Checkpoint
恢复检查点

某个安全时刻保存的任务状态快照。进程崩溃后从最近一次已提交检查点恢复，不必从任务开头重跑。

Lease
执行租约

Worker 临时持有某个任务的执行权，并带有到期时间。Worker 崩溃后租约过期，其他 Worker 才能接管，避免两个 Worker 同时执行同一步。

CAS
比较并交换式条件更新

数据库只有在记录版本仍等于读取时的版本，才允许更新。若另一个 Worker 已经更新，旧 Worker 的写入会失败，避免旧状态覆盖新状态。

Trace
链路追踪记录

用同一个 trace_id 串起一次请求经过的 API、模型、检索、工具和数据库操作，定位延迟和失败发生在哪一段。

RAG 检索与知识处理 10 个术语
RAG
检索增强生成

先从企业文档或知识库找证据，再把证据交给模型生成答案。它不是模型训练，也不是只做向量搜索。

ACL
访问控制列表

记录某份文档允许哪些用户、角色或租户访问。检索时必须先按 ACL 过滤，不能先召回再把无权文档交给模型。

Chunk
文档切片

把长文档按标题、段落、表格或代码结构拆成可检索的小块，并保留页码和文档版本，方便命中后回到原文。

Embedding
文本向量表示

把文本转换成一串数字，使语义相近的文本在向量空间里更接近。它擅长找同义表达，但对订单号、错误码等精确字符串不一定可靠。

BM25
关键词相关性排序算法

根据查询词在文档中的出现频率和稀有程度排序，适合精确查型号、编号、错误码和专有名词。

RRF
倒数排名融合

把向量检索和关键词检索各自的名次融合，不直接相加两种量纲不同的原始分数。某个片段在两路都排得靠前，融合后通常更靠前。

Cross-Encoder
查询与文档联合精排模型

把问题和每个候选片段一起输入模型，判断二者是否真正相关。它比向量召回更细，但计算更贵，所以只重排前几十个候选。

Query Rewrite
查询改写

把“那它为什么失败”改写成带上前文实体的完整检索问题；只在指代不清或首轮召回不足时触发，避免无必要改写造成语义偏移。

OCR
图片文字识别

把扫描 PDF 或图片里的文字识别出来。识别结果仍需校验页码、表格结构和置信度，不能默认完全准确。

Rerank
检索结果重排

对初步召回的候选片段再次打分并排序，目的是提高最终送入模型的证据准确度。

可靠性、数据库一致性与并发 16 个术语
Idempotency-Key
幂等键

客户端为一次逻辑操作生成的唯一标识。相同用户用同一个键重试时，服务端返回原任务 / 原结果，而不是再创建一笔业务操作。

payload_hash
请求内容摘要

对规范化请求内容计算的哈希值，用来判断同一个幂等键是否被错误地拿去提交了不同内容。

Deadline
整条任务的截止时间

不是每个子调用都重新获得完整超时，而是所有模型、检索和工具调用共享同一个结束时刻，并为最终落库和收尾预留时间。

P95 / P99
95 / 99 分位耗时

P95 表示 100 次请求中约 95 次不超过这个耗时；P99 看更慢的尾部请求。比平均值更能暴露少数特别慢的调用。

RPM / TPM
每分钟请求数 / Token 数

模型供应商常见配额。RPM 限制请求频率，TPM 限制每分钟输入与输出 Token 总量；并发要同时受这两项约束。

Outbox
事务发件箱表

业务主表更新时，在同一个数据库事务里写一条待发布事件。这样业务提交成功后，即使进程崩溃，事件也不会丢。

Inbox
消费去重表

消费者记录已经处理过的 event_id，并设置唯一约束。消息队列重复投递时，消费者识别重复事件，不重复产生业务效果。

At-Least-Once
至少投递一次

消息系统保证尽力重投直到确认，因此消息可能重复。消费者必须幂等，不能假设每条消息只到达一次。

Exactly Once
恰好一次效果

跨数据库、消息队列和外部 API 通常很难保证端到端只传一次；工程上更常用至少一次投递，加唯一事件 ID、幂等写入和对账实现业务效果不重复。

DLQ
死信队列

多次处理仍失败的消息被转移到隔离队列，保留原始内容和错误，供排查、修复后重放，避免阻塞正常消息。

Saga
跨服务补偿事务

多个系统不能放进同一个数据库事务时，把流程拆成多个本地事务，并为已成功的步骤定义补偿动作。例如订票成功但付款失败，就触发退订。

Backpressure
背压 / 过载反馈

队列或下游容量快满时，系统减慢生产、排队或拒绝新请求，而不是无限堆积任务把延迟和内存拖垮。

Circuit Breaker
熔断器

某个依赖持续失败时暂时停止向它发送普通请求；恢复后只放少量探测请求，避免故障服务被重试流量继续压垮。

UNKNOWN_COMMIT
提交结果未知

调用方超时，但第三方可能已经完成写操作。此时先查外部单号或幂等键对账，不能直接重试，否则可能重复创建或扣款。

Retry-After
建议重试等待时间

下游返回限流响应时给出的等待秒数或时间点；客户端按它延迟重试，而不是马上继续冲击服务。

Saga Compensation
补偿动作

对已经完成的业务步骤执行反向或修正操作；它不是数据库回滚，可能失败，也必须单独记录和重试。

评测、发布与运维 10 个术语
LLM Judge
大模型评审器

用另一个模型按评分标准评价答案质量；它可能有偏差，所以不能替代确定性业务校验和人工抽样。

Gold Chunk
标准证据片段

评测集里人工确认的正确文档片段，用来检查检索是否把真正相关的资料召回。

Recall@K
前 K 个结果召回率

正确证据是否出现在检索前 K 个候选中；主要衡量召回阶段有没有把答案依据找出来。

MRR
平均倒数排名

正确证据排得越靠前，分数越高；适合衡量第一个正确结果出现得有多早。

NDCG
归一化折损累计增益

同时考虑多个结果的相关等级和排序位置，越相关的结果排得越前，分数越高。

Canary
金丝雀发布

先让少量真实流量使用新版本，观察错误率、延迟和业务成功率；指标稳定后再逐步扩大流量。

Liveness
存活探针

判断进程是否还活着、是否卡死；失败通常触发重启。

Readiness
就绪探针

判断实例是否已经准备好接收流量；数据库迁移未完成时可以暂时不就绪，但不一定要重启进程。

PITR
时间点恢复

利用数据库备份和日志，把数据库恢复到某个历史时间点，用于误删或数据损坏后的恢复。

RPO / RTO
可接受数据丢失量 / 恢复时间目标

RPO 回答最多能丢多少时间的数据，RTO 回答故障后最多多久恢复服务；需要通过真实恢复演练验证。

仍需项目方明确的配置决策

这些不是架构逻辑缺失，而是必须由业务 SLA、安全规范和部署规模确定的参数；不能在通用架构图里伪造统一答案。

01 · 多租户隔离模型

明确采用共享库 tenant_id 行级隔离、Schema-per-tenant，还是 Database-per-tenant；同时定义跨租户管理角色和数据导出边界。

02 · 身份与权限模型

选定 OIDC / IdP、角色与 Scope 映射、资源 ACL 数据源、权限撤销生效 SLA，以及审批人授权和职责分离规则。

03 · 中间件选型

明确关系库、队列 / 事件总线、Redis、对象存储、向量库、BM25 引擎和部署平台；并定义各组件不可用时的降级能力。

04 · 操作风险矩阵

逐个业务动作定义副作用等级、是否需发起人确认、是否需独立审批、审批角色、payload 绑定字段和审批 TTL。

05 · SLA 与预算

按任务类型定义端到端 Deadline、排队预算、Token / 工具预算、并发配额、重试上限、队列硬阈值和 429 / 503 策略。

06 · 外部幂等能力

逐个写工具确认第三方幂等键语义、业务单号查询能力和对账 API；缺少这些能力的工具不得承诺 exactly-once。

07 · RAG 与 Memory 参数

按文档类型校准 Chunk / Top-K / Rerank 门槛；按记忆类型确定 TTL、用户查看 / 更正 / 删除流程和派生索引清理 SLA。

08 · 运营目标

定义各风险等级 SLO、P95 / P99、错误预算、Canary 回滚门槛、RPO / RTO、审计保留期和灾备演练频率。

本版设计审查：已修正的高风险模糊点

不是单纯增加术语，而是修正顺序、状态边界、决策责任和失败收敛条件。

01 · 上下文顺序

先构建路由前最小上下文；策略确定数据源后，再检索 RAG / Tool；最后组装完整模型上下文，避免“先要 RAG 才能判断是否要 RAG”的循环。

02 · 路由维度

数据来源、执行组织方式、风险门禁分开判断；RAG + Tool + Agent 可以组合，不再把它们做成互斥单选。

03 · 决策责任

LLM 只提取意图候选和槽位；权限来自身份 / ACL 服务，风险来自动作元数据，复杂度来自任务依赖图，策略引擎产出 RoutePlan。

04 · 工作流边界

固定步骤和固定分支用 Workflow / DAG；只有后续动作要根据 Observation 动态改变时，才启动 Agent Planner。

05 · 状态边界

Task、Step、Operation、Delivery 四套状态分开；补齐澄清、用户确认、独立审批、重规划、恢复、取消和未知提交的返回路径。

06 · RAG 证据门槛

不把线上“Recall@K”当成可直接观测值；用召回候选、精排分数校准、子问题覆盖、来源和时效判断证据是否足够。

07 · 数据库事务

补充唯一约束、CAS、原子 claim、TaskEvent / Outbox / Inbox 的区别、索引版本和连接池容量治理。

08 · 超时与取消

Deadline 从受理时刻开始计入排队时间；有未知写提交时先对账，不能直接结束为 TIMED_OUT 或 CANCELLED。

03 / 任务状态机：不只看箭头，要看迁移条件

每个状态都给出中文含义；QUEUED、CLAIMED、EXECUTING 明确拆开，避免把排队、领任务和真正执行混成一个状态。

主链路 / Main Path

RECEIVED已接收→ VALIDATING校验中→ QUEUED排队中→ CLAIMED已领取→ PLANNING规划中→ EXECUTING执行中→ SUCCEEDED成功

分支 / Recovery / Exception Paths

WAITING_APPROVAL等待审批 NEEDS_CLARIFICATION等待澄清 REPLANNING重新规划 RETRY_WAIT等待重试 RECONCILING对账中 RECOVERING恢复中
PARTIAL部分完成 FAILED失败 TIMED_OUT超时 CANCEL_REQUESTED取消请求中 CANCELLED已取消 ABORTED主动终止 REJECTED已拒绝

Task 状态只描述整项任务；Step 状态描述单个步骤；Operation 状态描述外部副作用是否提交；Delivery 状态描述单个订阅者的事件交付。GATHERING_EVIDENCE 是可选任务阶段；Full Context 在每次模型调用前按最新版本组装，不单独形成 Task 状态。QUEUED 是等待 Worker，CLAIMED 是 Worker 获得租约，EXECUTING 是至少一个 Step 正在运行。WebSocket 断开只影响订阅，不取消 Task。

Task State（任务状态）

RECEIVED、VALIDATING、QUEUED、CLAIMED、PLANNING、GATHERING_EVIDENCE、EXECUTING、WAITING_CONFIRMATION、WAITING_APPROVAL、NEEDS_CLARIFICATION、REPLANNING、RECONCILING、RECOVERING、CANCEL_REQUESTED、PARTIAL、SUCCEEDED、FAILED、TIMED_OUT、CANCELLED、ABORTED、REJECTED 等。

Step State（步骤状态）

BLOCKED → READY → RUNNING → SUCCEEDED / FAILED / SKIPPED / CANCELLED；瞬时失败可进入 RETRY_WAIT。多个 Step 可同时处于不同状态。

Operation State（外部操作状态）

NOT_STARTED → IN_PROGRESS → SUCCEEDED / FAILED / UNKNOWN_COMMIT；需要补偿时进入 COMPENSATING → COMPENSATED。它决定写操作能否安全重放。

Delivery State（交付状态）

按订阅者维护 PENDING → SENT → ACKED；客户端 ACK / last_event_seq 只表示收到事件。Outbox 的 PENDING / PUBLISHED 是独立发布状态；交付失败不回滚已提交的 Task 结果。

状态机需要落库什么？

task_id、tenant_id、status、state_version、plan_version、current_step、deadline_at、lease_owner、lease_until、cancel_requested_at、last_event_seq、terminal_reason、updated_at。状态快照负责快速恢复，事件日志负责审计与重放。

状态机最重要的四条不变量

① 终态不可被普通事件重新打开；② 状态迁移必须校验合法边与 version；③ 未知外部提交不能直接重试；④ 任务成功必须先持久化最终结果，再发送 done 事件。

04 / 意图识别与路由：系统到底根据什么做决定？

不是让 LLM 四选一：规则层处理确定条件，分类器 / LLM 只输出结构化候选，策略引擎按固定规则做最终路由，服务端权限与风险门禁优先级最高。

01 · INPUT路由前最小上下文

当前消息、最近有效轮次、未完成目标、已解析实体；此时不预先塞入整库 RAG 和长期 Memory。

02 · RULES确定性规则

解析固定命令和明确字段；认证、租户、权限硬门禁由服务端执行，不交给 LLM 判断。

03 · CLASSIFY语义解析

必要时由分类器 / 结构化 LLM 提取意图候选、实体、槽位、来源需求、动作候选和歧义标记；不授予权限。

04 · POLICY服务端策略决策

重查 Principal / ACL；计算风险和任务复杂度；检查槽位、能力、预算、截止时间，再生成 RoutePlan。

05 · ROUTE组合式路由

数据来源 × 执行方式 × 风险门禁；例如 Agent + RAG + Tool，而不是互斥单选。

意图识别输入特征：不是只看关键词

语义与上下文

当前消息语义、最近有效对话、代词指代、未完成目标、用户纠正、实体关系、时间与范围约束。

任务结构

目标数量、必填槽位、步骤依赖、是否需要循环观察、是否跨系统、是否存在分支和失败补偿。

服务端能力与授权信息

策略引擎查询工具目录、租户启用范围、Principal 的有效 Scope、资源 ACL 和工具健康状态。权限与健康不是 LLM 的分类输出。

服务端风险与预算

风险按工具副作用等级、资源敏感度和可逆性计算；复杂度按步骤依赖 / 分支 / 循环计算；再检查 Token、工具调用、Deadline 和供应商配额。

路由决策矩阵：三个维度分别判定，不能把它们做成四选一

判定维度可选结果由谁依据什么决定
数据来源当前对话 / 通用知识；内部资料 RAG；外部实时系统 / Tool策略引擎根据用户明确要求、问题涉及的数据域、来源目录和时效要求决定。LLM 只能提出“可能需要什么来源”的候选。
执行组织方式直接回答；单个原子能力调用；固定工作流；动态 Agent根据业务步骤、依赖边、分支、循环和中间结果是否改变后续计划决定；不是按句子长度或工具数量决定。
风险门禁允许；补充参数；用户确认；人工审批；拒绝服务端根据 Principal、资源归属、工具副作用等级、资源敏感度和审批策略决定。模型不能授予权限，也不能批准自己提出的操作。

真正可执行的路由规则：先判断“需要什么”，再决定“怎么执行”

先定义边界：RAG / Tool 描述“去哪里取数据或执行能力”；Direct / 单工具 / 固定工作流 / 动态 Agent 描述“怎么完成任务”；澄清 / 审批 / 拒绝是执行门禁。它们不是同一层级。例如一次任务可以是“动态 Agent 编排 + RAG 检索 + Tool 查询 + 写操作审批”。

一、路由前的固定处理顺序

  1. 先做确定性校验：认证、租户归属、请求格式、速率限制和安全策略。身份无效、租户越权或明确禁止的请求，直接拒绝；不让 LLM 决定是否放行。
  2. 再理解任务：格式固定、字段明确的命令由规则解析；自然语言歧义、多轮指代或多目标请求才调用分类器 / LLM。模型只提取候选意图和槽位，解析阶段不执行工具。
  3. 校验解析结果：服务端验证输出 Schema、字段类型和必填槽位；“上次那个实验”必须解析到唯一 experiment_id。模型结构不合法时允许一次受约束的格式修复；仍失败就返回解析错误，不得猜测资源 ID。
  4. 最后由策略引擎路由：权限从身份 / 授权服务读取；风险从工具目录的副作用等级、资源敏感度和可逆性计算；复杂度从任务图的依赖、分支和循环计算。模型不提供最终权限、风险等级或执行模式。

二、各类行为的硬触发条件（以下分类不是互斥路由选项）

路径 / 决策满足什么条件才触发明确不属于这条路径的情况例子与系统动作
Direct Answer
直接回答		答案的全部依据已在当前消息 / 已授权的会话上下文中，或属于稳定通用知识；不依赖租户私有文档、不依赖“现在”的外部状态、不产生外部副作用；所需实体和范围均明确。短附件若已被安全提取并完整放入当前上下文，也可直接总结。只要答案需要查内部文件、未加载的长附件、数据库当前值、外部 API，或需要改变外部状态，就不能走纯 Direct；必须增加相应数据源或执行步骤。“解释什么是过拟合” → 直接回答；“总结我刚贴出的这段文字” → 基于当前输入总结。
RAG
知识检索		用户明确指定 SOP / 内部规范 / 私有资料，或问题涉及企业知识域且答案必须以这些文档为依据时触发。检索前按 tenant_id、user_id、document_id 和当前 ACL 过滤；向量检索与 BM25 必须使用同一权限范围。“分析”“解释”“总结”这些动词本身不是触发条件。若用户提供的短文本已在上下文中，直接基于该文本回答；若需要从长文档集合中定位证据，才走 RAG。“按公司的实验 SOP 解释这次操作是否合规” → 检索 SOP；没有权限或没有证据时明确说明，不能拿其他租户文档补齐。
Atomic Capability
单原子能力调用		需要查询会话外的实时业务状态，或执行一个有明确输入、单一业务结果和独立验收条件的原子能力；目标对象、必填参数和授权均已确认，不需要根据中间结果动态决定下一步。一次 API 调用不等于一个原子业务操作，需按实际副作用判断。如果一个业务动作内部包含多个副作用、需要按中间结果改变后续步骤，或需要跨系统补偿，就不能仅因它包装成一个 Tool 而视为简单单工具任务。固定、可预定义的步骤可走固定工作流；动态决策才升级为 Agent。“查询实验 E-102 当前状态” → 调用一次只读查询工具；“创建一条实验记录” → 校验权限、参数和幂等键后执行，写操作按风险规则确认。
Agent Workflow
多步骤工作流		出现动态规划需求时才进入 Agent：工具 / 检索结果会改变后续计划；需要按观察结果选择分支；需要循环检查直到满足业务条件；任务中途可能重规划。若步骤固定、分支固定、验收规则固定，即使跨多个系统，也优先用确定性 Workflow / DAG 编排，不必调用 LLM 做动态规划。长文本、长答案、多个并列但互不依赖的只读查询，都不自动意味着需要 Agent。工具数量也不是唯一标准；核心判断是是否需要基于中间观察动态改变后续行动。“读取 E-102 实验数据 → 查 SOP → 对比历史记录 → 生成固定格式报告”，若步骤和分支预先确定则用 Workflow；若某项证据会决定下一步追加查询、循环验证或改写计划，才升级为动态 Agent。
Clarification
澄清补充		工具 Schema 标记为 required 的字段缺失；实体解析返回 0 个或多个候选且无法按确定规则消歧；时间 / 范围冲突；或分类结果处于该意图经验证集校准的拒判区间。只有会影响目标对象、数据范围或副作用的歧义才打断执行。权限不足不是澄清问题；系统不能通过追问让用户“补出”本来没有的授权。“把它删掉”但上下文有多个文件 → 询问具体文件；“查上次实验”但存在多个实验 → 询问实验编号或日期。
Confirmation
用户二次确认		操作由当前用户发起且该用户有权限；动作策略要求在不可逆 / 高影响副作用前，再由发起人确认最终对象、参数和影响范围。确认只证明发起人确认了这次具体操作，不增加权限，也不替代独立审批。确认必须绑定 payload_hash、资源版本和有效期；参数变化后重新确认。“删除项目 P-17” → 展示项目名、影响范围和不可恢复提示；用户确认后再执行。
Approval
人工审批		动作策略要求独立审批人复核；发起人本身仍须有执行权限，目标和参数完整。审批人必须具备 approver Scope，且不能由发起人自批。审批只解除风险门禁，不授予发起人权限；执行前重查发起人权限、审批人权限、资源归属、payload_hash、资源版本和审批有效期。“把分析报告发给客户” → 固化收件人和内容 Hash，创建审批单；独立审批人批准后再次校验并发送。
Refusal
拒绝执行		已认证请求若租户隔离失败、缺少必需 Scope、资源 ACL 不允许、命中禁止策略或没有获准的能力实现，则拒绝执行；拒绝结果不得通过澄清或审批绕过。入口认证失败属于 HTTP 401，不进入这条 Task 路由。不能因为 LLM 置信度高、工具语义匹配或用户催促，就跳过拒绝条件。用户只有 orders:read，却请求取消订单 → 服务端拒绝写操作；可以提示其申请相应权限。

三、意图到底由谁判断？职责边界如下

规则层

识别固定命令、明确操作、必填字段和硬性安全边界；确定性强、结果可复现。

分类器 / LLM

只输出 intent_candidate、entities、slots、knowledge_source_candidate、live_data_need、action_candidate、subgoals、ambiguity_flags。模型自报 confidence 只作弱信号；不输出最终权限、风险等级或审批结论。

策略引擎

服务端读取 Principal / ACL / Tool Registry；按动作元数据计算风险、按任务图计算复杂度，再产出 RoutePlan：data_sources、execution_mode、required_capabilities、approval_policy、deadline 和预算。

Controller

执行 RoutePlan 并维护 Task / Step 状态。固定步骤固定分支用 Workflow；只有后续动作需由新 Observation 动态决定时，才让 Agent Planner 重规划。

固定 Workflow 与动态 Agent 的边界：如果业务步骤和分支在设计时已知，例如“先查订单、再查物流、最后生成固定格式摘要”，用普通 Workflow / DAG 执行即可；如果必须根据工具返回或新证据决定下一步查什么、是否循环、是否改计划，才需要 Agent Planner。多工具并行本身不等于 Agent。

四、冲突时按什么优先级处理？

1. 身份 / 租户校验→2. 权限 / 安全硬拒绝→3. 必填槽位与歧义→4. 数据来源与执行模式→5. 副作用前确认 / 审批→6. 执行与验收

置信度如何使用：LLM 自报的 0.9 不是“90% 正确”的统计概率。只有经过标注验证集校准的分类器分数，才可按意图类别和误判成本设拒判阈值；LLM 结构化解析则主要看必填槽位、实体候选数、歧义标记和二次判别结果。没有经过校准就不设置通用数字阈值。无论置信度多高，权限和高风险审批都必须由服务端独立执行。

五、拿一个真实请求走完整条判断链

用户请求

“帮我分析实验 E-102 为什么失败，结合公司 SOP 和过去类似实验，最后生成一份报告。”

结构化理解

目标：失败原因分析 + 报告；对象：E-102；需要实时实验结果；需要内部 SOP 和历史案例；多个数据源；存在分析依赖，但不要求修改外部业务数据。

策略引擎决定

先用固定 Workflow 读取实验数据并检索 SOP / 历史案例；如果观察结果触发未预设的追查分支，再由 Agent Planner 动态重规划。数据来源是 RAG + 只读 Tool，执行模式由实际是否需要动态决策决定。

执行中如何变化

若实验 ID 不存在 → 停止并澄清；若 SOP 无权限 → 不检索该文档并报告缺失；若实验系统超时 → 按只读调用策略有限重试；若证据不足 → 标记结论不确定，不编造根因。

置信度怎么用？

不使用通用固定阈值。若使用监督分类器，按意图类别在独立验证集上校准分数，并根据误判代价设拒判区间；若使用 LLM 解析，则以 required_slots、实体候选数、ambiguity_flags 和二次判别结果决定是否澄清。模型自报分数不作为授权或审批依据。

复杂度如何判断？

不按字数或工具数量计分。先形成候选步骤图，再统计依赖边、条件分支、循环观察、外部系统边界和副作用；固定图走 Workflow，必须根据 Observation 改图才走动态 Agent。风险单独由动作元数据和资源敏感度计算。

面试表达：我不会让 LLM 直接决定执行路径。模型只负责输出结构化候选意图与槽位，服务端策略引擎结合权限、风险、工具能力和预算做最终路由。对不确定且执行代价高的请求，优先澄清而不是猜测执行。

为什么每一阶段都存在

  • 解析：原始文件格式不统一，必须先变成可处理文本；表格、扫描 PDF、页眉页脚需要专门处理，否则噪声会进入索引。
  • 切块：整篇文档超出上下文窗口且检索粒度太粗；块太大带来噪声，块太小会丢失指代和上下文。Overlap 用来缓解边界截断。
  • Embedding：把语义映射到向量空间，解决“意思相近但字面不同”的检索问题；但它不擅长精确编号、代码符号和罕见词。
  • BM25：利用词频与逆文档频率做词项匹配，补足精确术语；对同义改写能力弱。
  • RRF：不同检索器分数不在同一量纲，直接加权容易偏向某一路；RRF 依据排名融合，工程上更稳健。
  • Rerank：初召回追求覆盖，允许多取候选；Cross-Encoder 对 Query 与候选文本联合编码，精度更高但计算更贵，因此只对候选集精排。线上没有 Gold Chunk，不能直接计算 Recall@K；应使用经过版本校准的精排分数、Top1/Top2 分差、子问题证据覆盖和来源有效性判断证据充分性。

可靠性：工具调用不是“调用成功 / 失败”二元问题

必须区分执行状态、提交状态、重试安全性与业务副作用

例如：调用“创建订单”时客户端超时，不代表订单没创建。外部系统可能已提交，只是响应丢失。此时如果直接重试，可能创建两笔订单。必须把“调用超时”和“业务提交结果未知”分开建模。

重试策略：先判断可重试，再执行退避

  • 瞬时故障：连接重置、429、部分 5xx、读超时，可按策略重试；优先尊重 Retry-After。
  • 永久故障：参数校验失败、权限拒绝、资源不存在，不重试，直接返回可解释错误。
  • 退避：指数退避 + 随机抖动，例如 0.5s、1s、2s，并设置最大次数和总耗时上限，避免雪崩。
  • 幂等：写操作生成稳定 idempotency_key；服务端以唯一键记录操作结果，同一 key 重放返回原结果。
  • 未知提交：进入 UNKNOWN_COMMIT / RECONCILIATION，先查外部系统或操作台账，不能盲目重放。
  • 补偿：跨多个系统的写操作采用 Saga 思路，定义反向补偿动作；补偿也要幂等且可审计。

超时：使用 Deadline，而不是每个请求各自随意等待

  • 入口创建全局 deadline，例如整轮任务最多 90 秒；所有下游调用继承剩余预算。
  • 为 LLM、Embedding、向量库、数据库、MCP / HTTP 工具分别设 connect / read / total timeout。
  • 预留收尾时间：执行预算到点前停止新工具调用，留时间整理结果、写入最终状态和发送 done。
  • 超时触发取消时，向下游传播 cancellation；但取消请求不等于外部副作用已回滚。
  • 区分排队时间、连接时间、服务端处理时间和总耗时，才能定位瓶颈。

并发：能并行不代表可以无限并行

  • 先把计划表达成依赖 DAG：无依赖的只读查询可并行，有前后依赖的步骤必须串行。
  • 用全局、租户级、模型供应商级、单工具级 Semaphore 限制并发；避免一个租户耗尽全部连接和模型额度。
  • 有界队列 + 背压：队列满时拒绝、降级或排队，不能无限堆积协程和内存。
  • CPU 密集解析 / OCR 放线程池或独立 Worker；网络 IO 用异步，避免阻塞事件循环。
  • 批量 Embedding、连接池复用、缓存只读元数据；限制单请求最大并行工具数。
  • 部分失败时保留成功结果，按依赖关系决定是否继续；不要简单地让一个工具失败拖垮整组任务。

隔离与熔断

  • Bulkhead：LLM、RAG、MCP、数据库使用独立资源池或并发配额，某个依赖故障不拖垮全站。
  • Circuit Breaker：连续失败后打开熔断，短暂拒绝请求；半开状态探测恢复，避免持续冲击故障服务。
  • Rate Limit：按用户、租户、API Key、工具和模型供应商限速；同时控制 Token / 日预算。
  • Sandbox：自定义代码在隔离进程 / 容器运行，限制 CPU、内存、执行时间、文件系统和网络出口。

一致性：多个存储系统之间不要靠“连续写两次”保证

关系库是事实源，向量索引、缓存和事件流是可重建的派生数据

① 请求接收事务

同一个 DB transaction 写入用户消息、任务记录和 Outbox 事件；提交成功才确认任务已受理。

② 异步消费者

Worker 拉取 Outbox，按 event_id 幂等消费；更新任务状态时用版本号 / CAS 防止并发覆盖。

③ 多存储索引

文档元数据在关系库；原文件在对象存储；向量索引与 BM25 是派生索引。失败可重放事件重建。

④ 记忆写入

回答交付不等待所有记忆索引完成；先可靠记录待处理事件，再异步摘要、去重、Embedding 和落库。

核心原则：不要宣称分布式系统天然“Exactly Once”。更可信的面试表达是：采用 At-least-once 投递 + 幂等消费 + 去重键 + 状态机 + 对账任务，达到业务效果上的一次性。

数据库落地：表、约束、事务边界和并发控制

把“一致性”落实到具体写入顺序；外部网络调用永远不放进数据库事务。

三个本地事务边界

  1. 受理事务 A：认证、基础 Schema 和同步限流通过后，写 Task(RECEIVED)、用户消息、幂等记录、初始 TaskEvent 和 task.validation_requested Outbox；提交后返回 202 + task_id。202 只代表异步受理，不代表业务授权已通过。
  2. 校验 / 状态事务 B：Validation Worker 完成 ACL、Scope、配额和业务前置校验后，用 state_version CAS 写 QUEUED + TaskEvent + task.execute_requested Outbox；失败则写 REJECTED + TaskEvent，不创建执行 Outbox。任一事务内写入失败都整体回滚。
  3. 步骤事务：外部调用返回后，写 Step Result、Operation 回执、Task State 和事件；调用外部 API 本身发生在事务之外。

并发写入与查询策略

  • Task 状态：UPDATE ... WHERE task_id=? AND state_version=?；影响行数为 0 表示版本冲突，必须重读。
  • Worker claim：原子条件更新或 SELECT ... FOR UPDATE SKIP LOCKED；同时递增 fencing_token。
  • 幂等：唯一索引处理并发插入竞争；同 Key 同 Hash 返回原结果，同 Key 不同 Hash 返回 409。
  • 鉴权、幂等和任务状态使用主库读，避免副本延迟造成错误放行或旧状态展示；报表可读副本。
  • 长文本和工具输出放对象存储；数据库保留引用、Hash、版本和必要摘要。
  • 连接池按所有 API / Worker 实例总量计算，预留迁移、监控和故障处理连接。

不要混淆：TaskEvent 是“发生过什么”的事实日志；Outbox 是“还需要发出去什么”的待投递记录；Inbox 是“这个消费者处理过什么”的去重记录。三者有不同生命周期。

记忆分层：不同信息使用不同生命周期

  • 会话 / 短期状态：当前对话窗口、当前任务计划、工具结果；跟随 Session / Checkpoint，适合快速读取和恢复。
  • Task Memory：类似任务如何完成、使用了哪些工具、是否成功、耗时与失败原因；支持相似任务复用。
  • Tool Memory：工具成功率、常见错误、参数偏好、适用场景；帮助模型选择更合适的工具。
  • User Profile：用户稳定偏好、语言、输出习惯、常用技术栈；要有用户可见、可编辑和删除机制。
  • Failure Pattern：错误签名、命中次数、修复策略、策略成功率；命中已知失败时可跳过昂贵反思。
  • Learning Parameters：阈值或权重调整；必须有边界、版本、变更来源和回滚能力，不能让模型任意改线上参数。

记忆检索为什么不能只做向量 Top-K

  • BM25 对精确工具名、错误码、API 名称更敏感；向量检索对语义相似任务更敏感。
  • RRF 先融合不同检索器的排名，再做业务加权，避免分数尺度差异导致偏置。
  • 成功经验权重高于失败经验，但失败经验仍有价值；注入时明确标记“历史失败教训”，防止模型把失败方案当成功模板。
  • 质量、时间衰减、复用次数、用户偏好共同决定排序；过期经验需要 TTL / 淘汰策略。
  • Top-K 必须受 Token Budget 限制；记忆是上下文提示，不是事实数据库，关键事实仍要查源系统。

回答成功与记忆写入失败，应该如何处理？

用户答案已交付→写入 Memory Outbox→异步提炼 / Embedding→Memory READY

系统将“用户请求成功”和“经验沉淀成功”拆成两个状态域。记忆是增强能力，不应因为 Embedding 服务短暂不可用就让已完成的用户任务变成失败。失败事件进入重试队列；超过重试窗口进入 DLQ，并支持人工重放。关键审计日志则不能随意丢弃。

用于项目介绍、架构追问和生产级系统设计的表达框架

90 秒项目介绍模板

我把这个项目理解为一个面向多租户的 Agent 执行平台，而不只是一个接了大模型的聊天应用。系统从请求入口开始，先完成身份、租户和会话校验，再把对话历史、知识检索结果和历史执行经验组装成有预算的上下文。随后由控制层判断任务复杂度，选择执行路线和可用能力。执行阶段采用受预算约束的循环：模型提出动作，工具执行后把结果规范化，再由监控层判断继续、重规划还是终止。对外部写操作，还需要审批、幂等键和操作台账，避免超时后的重复提交。任务完成后，系统交付流式结果，同时异步沉淀 Trace 和 Memory；离线评测再用成功率、工具选择、恢复率、延迟和成本验证改动是否真的提升质量。系统把一致性、并发、故障恢复、租户隔离和可观测性贯穿到每一层。

高频追问：为什么不用单一向量检索？

向量检索解决语义相似，不保证精确术语召回；BM25 擅长关键词和标识符。两路并行召回后用 RRF 融合，避免原始分数不可比，再用 Cross-Encoder 对候选精排。这样把高召回和高精度拆成两个阶段，并把昂贵模型限制在小候选集上。

高频追问：工具超时后能不能重试？

先看工具副作用和提交状态。只读操作通常可以有限重试；写操作必须有幂等键。若请求超时但提交结果未知，先按 operation_id 对账，不直接重放。否则会把网络层的不确定性变成业务重复执行。

高频追问：如何保证数据库与向量库一致？

不做跨存储伪事务。关系库保存文档元数据和索引任务状态，事务内写 Outbox；消费者异步构建向量与 BM25 索引，按文档版本和稳定 chunk ID 幂等写入。只有索引达到可用条件才发布版本；失败可重试、重建和对账。删除使用 tombstone，确保所有派生索引最终清理。

高频追问：并发工具怎么调度？

先根据计划依赖关系构造 DAG，只并行执行互相独立的步骤。全局、租户、供应商和单工具维度都设置并发上限；队列有界并提供背压。每个子任务继承全局 deadline，部分失败按依赖关系决定是否继续，写操作不因并行而绕过幂等和审批。

高频追问：Memory 与 RAG 有什么区别？

RAG 面向外部知识资产，强调文档解析、版本、权限、引用和知识更新；Memory 面向系统执行经验与用户偏好，强调任务结果、工具表现、失败策略、复用和时效。二者可以共享检索技术，但数据模型、写入触发、权限和生命周期不同。

高频追问：如何证明 Agent 变好了？

不能只看主观回答。建立固定任务集，分别度量任务成功率、路由准确率、工具选择准确率、重规划恢复率、记忆命中率、延迟分位数、Token 成本和安全拒绝率。版本对比使用配对任务和置信区间 / 显著性检验；通过质量门禁后灰度发布，并保留回滚路径。

面试时必须讲清楚的工程边界

  • 项目实现：围绕多租户请求路径、Agent 控制与反思、工具渐进式披露、混合 RAG、经验记忆、可靠性治理、数据一致性、Trace 和评测门禁形成完整闭环。
  • 系统工程机制：讲清楚 Outbox、任务队列、DLQ、分布式限流、熔断、灰度、版本化索引和可恢复执行的设计取舍、状态流转和故障边界。
  • 量化承诺：不要在没有压测和线上数据时声称具体 QPS、P99、召回率或成本下降比例。可以说清楚指标如何定义、如何压测、如何验收。
  • 系统边界：Agent 的“推理过程”不等于可信执行；模型给出的参数必须校验，工具权限必须由服务端执行，文档内容和工具输出必须视为不可信输入。
